## 1. 分层与依赖方向

```
Application/ (app_*)   业务：启动编排、协议、渲染与整屏、配置、按键、自检
      ↓
Device/      (dev_*)   设备抽象：OCP 虚表封装硬件差异（Display/IO/Network/Storage）
      ↓
Platform/    (pl_*)    HAL 薄封装：对外只给不透明句柄（void *），HAL 类型不出层
      ↓
Core + HAL             CubeMX 生成 + ST HAL + CMSIS
Kernel/                零依赖纯软件工具（ring_buffer/initcall/container_of/text_cvt/crc/bit/bcc）
Compiler/              startup.c（C 写的 Reset_Handler + 自定义向量表）、sections.ld、OpenOCD 配置
```

**依赖严格单向**：上层可见下层，反之不可。层前缀由"定义在哪个 `Inc/` 树"决定（`docs/命名约定.md` §1）。

**为什么要单向、为什么 Platform 只给不透明句柄**：
- 若 Application 直接摸 HAL，换芯片/换外设型号会污染整个业务层；
- 若 Platform 暴露 `SPI_HandleTypeDef*` 之类，HAL 版本升级会穿透到 Device/Application；
- 所以 Platform 的 API 一律 `void *` 句柄 + 语义化函数（`pl_spi_transmit`、`pl_uart_start_rx`…），
  HAL 类型只出现在 Platform 的 `.c` 里。**唯一的结构性约束是 `Platform/Inc/pl_net_adapt.h` 严禁被任何 `.h` 包含**
  （它聚合 LwIP 头，泄漏会把 middleware 类型带进 Application 层头文件）。

板级覆盖：`boards/<板>/` 下可以有与共享层**同名**的文件（`pl_eth_board.c`、`dev_rs485.c`、
`app_rs232.c`…），构建时按板选取。**共享层写"跨板相同"的部分，板级写"这块板的引脚/外设/模组"。**

## 2. 启动流程与 initcall

```
上电 → Reset_Handler (Compiler/startup.c)
  ├─ .data 拷贝、.bss 清零、CCMRAM(NOLOAD) 段清零
  ├─ SystemInit()（FPU、时钟骨架）
  └─ main() (boards/<板>/Core/Src/main.c)
       ├─ HAL_Init() / SystemClock_Config()（HSE 8MHz → 168MHz）
       ├─ initcall_run(__hw_initcall_start, __hw_initcall_end)   ← RTOS 之前
       └─ app_boot()      ← 编排
            ├─ osKernelInitialize() + osThreadNew(init_task, High)
            ├─ osKernelStart()
            └─ init_task:
                 ├─ dev_eth_start()        （LwIP + netif）
                 ├─ initcall_run_sw()      （__sw_initcall 段）
                 ├─ osThreadNew(half_sec_task)（喂狗 + LED）
                 └─ osThreadExit()
```

**initcall 机制**：宏把初始化函数放进链接段，`initcall.h` 提供 **9 个层级宏**——
`hw` 侧 4 层（`hw_pre`(0) / `hw_pl`(1) / `hw_dev`(2) / `hw_post`(3)），
`sw` 侧 5 层（`sw_pre`(0) / `sw_pl`(1) / `sw_dev`(2) / `sw_app`(3) / `sw_post`(4)）。
`initcall_run_sw()` 顺序遍历 `__sw_initcall` 段。

**关键约束：同层内的次序不可依赖。** 宏生成的段名同层完全相同（`.sw_initcall.3` 之类），
`SORT()` 排的是输入段名、对同层是空操作；实际次序就是目标文件在链接命令里的先后——
而 `Makefile` 与 `.eide/eide.yml` 各有一份文件清单，**未必一致**。
**要表达依赖请用层级**：例如"读配置"放 `sw_post(4)`，让 `sw_app(3)` 的"加载配置"先跑。

## 3. 内存与 CCMRAM

| 区 | 用途 |
|---|---|
| Flash 1MB @`0x08000000` | 向量表 + 应用（`.text/.rodata`，含 initcall 段）。IAP 记录占 Sector 1（`0x08004000`，仅带 IAP 的板） |
| SRAM 128KB @`0x20000000` | `.data/.bss`、FreeRTOS heap（32KB，heap_4）、LwIP 内存、环形缓冲区池、UART DMA 缓冲、各任务栈 |
| **CCMRAM 64KB @`0x10000000`** | 显示帧缓冲等**高频访问**数据（NOLOAD 段） |

**CCMRAM 为什么被挑中**：它与内核直连、**零等待状态**，不经总线矩阵，所以放在这里的缓冲
（显示扫描每行都要读）比放 SRAM 快。代价是**只能放数据、不能放代码**，且是 `NOLOAD` 段——
`startup.c` 里整体循环清零（行为等同 `.bss`，但不会被 `.data` 的拷贝过程碰）。

> 注意：具体哪些缓冲在 CCMRAM 由**板级驱动**决定（如 5006048 的 P10 驱动把自己的帧缓冲放进去），
> 不是全局固定的一串名字。改板级驱动时要确认段归属（`arm-none-eabi-objdump -h … | grep ccmram`）。

## 4. 中断体系与三级流水线

**原则：所有外设 ISR 内聚在 Platform 层的 `.c` 里**（不散落在 `stm32f4xx_it.c`），
且 ISR 内只做最小操作（标记/通知），耗时逻辑交给任务。

```
TIM3 行同步   ──→ osEventFlagsSet        ──→ scan_task（Realtime，最高优先级）
TIM4 PWM 调光 (ISR 内直接完成 OE 翻转，不唤醒任务)
UART 空闲中断 ──→ osMessageQueuePut       ──→ 该通道的任务（app_rs485_task / app_rs232_task …）
                                              └─→ app_ccb_dispatch → ch_queue
                                                    ──→ app_dispatch_task → 协议帧队列 → 协议任务
SPI DMA 完成  ──→ volatile 标志           ──→ dev_w25qxx 轮询消费
ETH 收包      ──→ osSemaphoreRelease      ──→ LwIP ethernetif 输入线程
HardFault     ──→ naked asm 保存现场（R0-R3/R12/LR/PC/xPSR/CFSR/BFAR）再打印
```

三种解耦手段的分工：**EventFlags** 用于"事件/周期"，**MessageQueue** 用于"带数据的逐级传递"，
**Semaphore** 用于"资源/连接生命周期"。中断优先级上 `configMAX_SYSCALL_INTERRUPT_PRIORITY = 5`，
即只有优先级 ≥5 的 ISR 里才能调 FreeRTOS API。

> **链路状态不会通知上层**：Platform 侧那个链路监听线程已删除；网线拔插靠各通道自己感知
> （UDP socket 自愈、TCP 靠 `recv` 返错重连）。IP 变更监听是另一套（`pl_net_register_ip_listener`）。

## 5. OCP 虚表模式

项目里所有设备与通道都用同一套"手写 C 虚表"，不依赖任何 OOP 语法：

```c
struct dev_storage { const dev_storage_ops_t *ops; uint32_t capacity; };  /* 基类：ops 必须在首位 */
typedef struct { dev_display_t base; /* 派生字段 */ } dev_display_p20_t; /* 基类对象必须是派生结构体首成员 */
dev_display_p20_t *p = container_of(display, dev_display_p20_t, base);    /* 零开销上转型 */
```

**基类对象在派生结构体里的成员名统一叫 `base`**（用 `container_of` 转型；`container_of` 展开成
`(char*)ptr - offsetof(...)`，偏移为 0 时与裸转型生成同样的机器码，但把"首成员"这个隐含契约写成了显式的）。

| 虚表 | 定义处 | 方法 | 实现者 |
|---|---|---|---|
| `dev_display_ops` | `Device/Inc/Display/dev_display.h` | `prepare` / `scan` / `set_row` | 各板级显示驱动 |
| `dev_storage_ops` | `Device/Inc/Storage/dev_storage.h` | `init/read/write/erase/capacity` | `dev_w25qxx`、`dev_flash_int` |
| `app_ccb_ops` | `Application/Inc/app_dispatch.h` | `send` | 各传输通道（UART/TCP/UDP/MQTT） |
| `app_pcb_ops` | `Application/Inc/app_dispatch.h` | `probe` | 各协议（IAP/LDI/RLS/AHMQ） |

**边界纪律**：跨模块只暴露 **API**；`g_` 变量只允许在**本模块的 `Inc/` 头**里声明，
跨模块使用必须走 API（`docs/命名约定.md` §4.7）——例：LDI 取 IAP 的网段配置走
`app_iap_get_net_cfg()`，而不是直接解引用 IAP 的映射指针。

## 6. 协议分发引擎

引擎的形态：**协议控制块（`app_pcb_t`）绑定到通道控制块（`app_ccb_t`）**。

```c
app_pcb_t = { name, ops->probe, rb(环形缓冲), queue(帧队列), payload_max, internal_bus }
app_ccb_t = { name, ops->send, state, protos[≤4], proto_cnt }
```

数据流：

```
通道任务收到字节
  └─ app_ccb_dispatch(ccb, src, data, len)
       ├─ 写入该 ccb 上**每个**已绑定 pcb 的环形缓冲（同一份字节喂给多个候选协议）
       └─ osMessageQueuePut(g_dispatch.ccb_queue, &ccb)
            └─ app_dispatch_task
                 └─ 对每个 ccb 的每个 pcb 调 probe()：
                      READY  → 读整帧 → 投到该协议的 frame_queue
                      WAIT   → 数据不足，等更多字节
                      FAKE   → 伪帧头，跳过 1 字节重试
                      SKIP   → 帧结构合法但不属于本设备，跳过整帧
```

**为什么"同一份字节喂给多个协议"**：总线是共享的（RS485 上可能同时跑 IAP 与级联），
谁认领由 probe 判定，框架不预设通道与协议的对应关系。**发送**走 `app_ccb_send` /
`app_ccb_send_to`（后者带目标地址，用于级联的定向回包）。

新增一个协议 = 写 probe + 定义载荷结构 + `app_dispatch_bind()` 到通道 + `sw_app_initcall` 自注册
+ 在协议任务里消费自己的 `frame_queue`。**不改动引擎**。

> **帧长硬上限**：`FRAME_DATA_MAX_LEN = 1440`（`app_dispatch.h`）。它是"级联一帧一轮"成立的前提——
> 新协议的 `payload_max` **不得超过它**，超了帧就投递不上来（引擎按该值给每个协议分配暂存）。

## 7. 显示子系统

### 7.1 设备层（`Device/`）

`dev_display_t` 描述"一块屏"：模组参数（`module_rows/cols`、`channels_per_module`、
`modules_per_row/col`）→ 派生出屏几何（`screen_rows/cols`、`channels`、`channel_pixels`、
`scan_line_pixels`）；通用 API 是 `set_pixel` / `fill` / `draw_bitmap` / `set_brightness`，
**几何全是运行期值**（没有编译期宏）。

具体模组在**板级驱动**里（按料号命名）：`dev_p20_16x8_…c`（3833024 用，128×32 静态扫描）、
`dev_p10_112x10_…c`（5006048 用，224×50、1/2 扫、A/B 交叉），另有备用模组。每个驱动实现
`prepare/scan/set_row`，在初始化时**预计算 BSRR 查表**，并按模组灯珠实况填 `supported_color_mask`。

### 7.2 扫描架构（实时性关键）

```
TIM3（行同步，频率 = 刷新率 × 扫描行数）
  └─ ISR: osEventFlagsSet → scan_task（osPriorityRealtime，不会被用户任务抢占）
       1. 若 dirty：ops->prepare(dev)   ← pixel_map → hub75_buff（位重排，在临界区外做）
       2. ops->scan(dev, line)          ← 查预计算表 + CLK 脉冲
       3. OE/LAT 原子窗口（osKernelLock + 关 TIM4 中断）
TIM4（PWM，频率 = TIM3 × 8）
  └─ ISR: OE = (pwm_cnt >= light_level)，8 级亮度由"哪些行亮"直接实现
```

**为什么 prepare 在临界区外、扫描只查表**：单条扫描线的时间预算极紧，任何分支/位运算都会挤占；
颜色→BSRR 的查表在初始化时算好，扫描时只做"取表 + 写寄存器"。

颜色是 **3 位编码**（bit0=R/bit1=G/bit2=B）的 `dev_display_color_t`（8 色），
`pixel_map` 存颜色值、prepare 时按调色方案展开。**一个模组能显示哪些颜色是运行期能力**
（`supported_color_mask` + `dev_display_supports_color()` / `dev_display_color_mask()`）：
不支持的通道就是灯珠没装，硬件实际呈现 = `颜色 & 掩码`（**位与即物理现实**，故不做
"最近似色"降级）；消费方是工厂逐色老化 —— 按能力枚举可用色（P20 三色 / P10 七色）。

### 7.3 整屏门面与级联（`Application/…/Render/`）

**多卡级联时**，主机发来的是"整屏"内容，比单卡自己的屏大；主卡要把它切开、自己显示一块、
其余经 RS485 下发。`app_screen` 就是这层的门面（**凡是影响整屏的动作都从它过**，级联协议只认它）：

| 关注点 | 实现 |
|---|---|
| **切分表** | 整屏分成 `nx×ny` 格，每格 `{addr, color, x, y, w, h, state}`。**总线地址 ≠ 格子下标**（主卡可在任意一格，如"下面那块是主卡"） |
| **1bpp 逻辑画布** | 整屏大小的位掩码（只记亮/灭，`(宽+7)/8` 行字节、MSB-first）。**只在 `BOARD_SCREEN_CANVAS=1` 时存在**——单卡板上它是纯开销 |
| **渲染目标** | `app_screen` 实现 `app_render_target_t`（`fill`/`bitmap`）并注册给渲染引擎，于是引擎排版直接写进画布，**引擎一行都不改** |
| **抽带与落屏** | `app_screen_extract(card_idx,…)` 从画布抽**任意一张卡**那块矩形（与 `dev_display_draw_bitmap` 逐位一致 → 从卡零转码直接吃）；`app_screen_commit_self()` = 抽本卡那块 + 落本地屏。**主卡本地提交与抽给从卡走同一个 extract**，这是同步显示一致的根据 |
| **颜色** | 画布只记亮/灭；"这一帧用了哪个非黑颜色"另行记账，落屏时用（1bpp 表达不了多色时退回落切分表给该卡的颜色） |
| **身份** | 运行期事实：**拨码 > `casc_id` 记录 > 板级默认**。按键认领会写记录（掉电不忘） |
| **亮度** | 唯一入口 `app_screen_set_brightness()`；"待下发"标志把每秒可能变多次的亮度**攒成一次广播** |

**代码组织**：同模块按职责拆 4 个 TU——`app_screen.c`（切分表/身份/初始化与组合根）、
`_canvas.c`（画布、抽带、持久化、轮询；**整 TU 由 `BOARD_SCREEN_CANVAS` 守卫**）、
`_status.c`（卡在线/离线/告警/快照）、`_brightness.c`。跨 TU 只经**访问器**，内部状态各自保持 `s_`。

**级联协议**（`Application/…/CASC/`）：一轮 = 主卡给每张从卡下发一张**整块位图**（`IMAGE`，0x01）+ 本轮参数；
从卡收齐后本地提交（`app_screen_commit_self()`），应答 `ACK`（**无载荷**）或 `NACK`（**1 字节拒收原因**）。
共 **7 种帧**：主→从有 `IMAGE`/`PING`/`SET_ADDR`/`SET_BRIGHT`，从→主有 `PRESENT`/`ACK`/`NACK`
（方向靠帧类型的 `0x20` 位区分）。主卡（总线地址 0）负责枚举、开轮、分级失败剔除与定向重传。
**画布与级联是单向约束**：板级 `#error` 只保证"**多卡 ⇒ 必须有画布**"（否则主卡无从切分下发）；
单卡板合法地开画布是允许的。

## 8. 存储与配置

### 8.1 两级存储与统一虚表

`dev_storage_t`（`ops: init/read/write/erase/capacity`）+ 便捷内联（`dev_storage_read(...)`）。
两个实现：**W25Qxx**（SPI NOR，JEDEC 自识别容量；半双工 DMA 读 + 读-改-写整扇区写）、
**内部 Flash**（内存映射读，按 word 编程，按扇区擦除）。

### 8.2 通用配置记录层

- `dev_cfg_record`：**24B 固定头 `{name[16], version, len, crc32}` + 载荷**。
  状态 EMPTY/INVALID/IO_ERR/OK。名字匹配 + version + 长度 + CRC32 四重校验；保存时读回比对，
  内容一致就跳过擦写。
- `app_cfg_sched`：**配置区 = W25Qxx 最后 8 × 4KB 扇区**，按"块"归属给各所有者（渲染帧、级联身份、LDI 配置…）。
  块的归属在**启动扫描时按记录 `name` 决定**（不是注册顺序），首启才回落到注册槽。

### 8.3 内部 Flash 的 IAP 记录

`app_iap_cfg.c` 把 `0x08004000`（Sector 1）内存映射成 `app_flash_iap_sys_info_t`
（magic + 升级状态 + 固件信息 + 网络配置 + CRC32）。**只有带 IAP 的板才有这条记录**
（`BOARD_HAS_IAP_RECORD`）。跨模块读它必须走 API（`app_iap_get_net_cfg()`）。
`dev_flash_iap.c` 这个旧模块已不存在——记录管理全在 `Application/…/IAP/`。

> **记录名与布局是落盘契约**：`name[16]` 字符串、字段偏移都是"改名即丢数据"，见 `docs/命名约定.md` §13。

## 9. 网络子系统

```
dev_dp83848（PHY：寄存器/自协商/链路查询，经 IO 上下文注入与 MAC 解耦）
    └─ pl_eth（ETH MAC/DMA；注册 PHY 链路查询回调）
         └─ pl_net（LwIP netif、IP 配置、IP 变更监听）
              └─ 通道：UDP / TCP server / TCP client / MQTT
```

- **PHY 与 MAC 的解耦**：`dev_dp83848` 通过函数指针（`pl_eth_phy_io_*`）访问 MDIO，不直接碰 MAC。
- **lwipopts 要点**：内存 12KB、校验和卸载到硬件、广播开启（IAP 依赖）、MQTT 使能、TCP keepalive。
- **`pl_net_adapt.h` 只许 `.c` 引用**（见 §1）。
- **链路状态不通知上层**：拔插由各通道自己感知（见 §4 末尾）。

## 10. 协议

| 协议 | 帧格式 | 绑定通道 | 状态 |
|---|---|---|---|
| **IAP** | 帧头 `0x5A5A5A5A` + seq + cmd + len + data + **CRC32**（按 4B 字对齐） | **RS485 + UDP**（3833024 另加两路 RS232） | 活跃，8 条命令：`0x00` 测试 / `0x01` 报告 IP / `0x02` 强制改 IP / `0x03` 报告固件状态 / `0x04` 准备升级 / `0x05` 下发升级包 / `0x06` 进入 Recovery / `0x07` 重启 |
| **LDI** | `STX = 0xFFFF` + ver + seq + len(4) + data + **CRC-16/XMODEM** | TCP server + TCP client + UDP | 活跃，12 条命令（0AH–21H）。设备类型枚举 12 个（`0xE1`–`0xEB` 与 `0xF4`），`APP_LDI_DEVICE_COUNT = 12` 与之一致（该常量只表数量，代码中无引用者） |
| **RLS** | `FF FE` + len(2, 大端) + cmd(2) + data + BCC + `0D 0C` | 仅 RS485 | 活跃，3 条命令（测试 / 显示 / 显示并保存）；**BCC 校验当前被注释掉** |
| **AHMQ** | 固定帧（21~533B），NUL 结尾，按 MQTT topic 路由 | MQTT | **未激活**：initcall 被注释，且源码已进 `Makefile` 的 `SRC_EXCLUDE`（**所有板都不编译**，EIDE 两目标同步 exclude）。重新启用前须先修 `app_ahmq_cmd.c` 中 `_cmd_display` 的 `cvt_utf8_to_gbk` 调用点：把输入夹到 ≤ `sizeof(gbk_txt)`（128）并初始化 `gbk_len`（`toSize` 是纯输出、不带容量语义） |
| **CASC** | 见 §7.3 | RS485（标记 `internal_bus`，不通知上层监听器） | 活跃（仅级联板） |

协议目录各自独立（`IAP/ LDI/ RLS/ CASC/ AHMQ/`），新增协议见 §6。

## 11. 渲染引擎（字库）

`app_render` 是**数据驱动**的字库引擎：字库数据在 W25Qxx 上，**板级** `g_board_font_lib`
（`app_font_lib_desc_t`）描述"本板有哪些字号/字型/编码"，单元在 Flash 里从地址 0 起**线性连续**排列，
所以起始偏移 = 前面各项 `unit_size` 之和。

- **三处同一约定**：画布位图、`dev_display_draw_bitmap`、持久化记录的位序**逐位一致**
  （`(宽+7)/8` 行字节、行优先、MSB-first、bit=1 上色）——所以"画布抽出的位图"从卡可以直接吃，零转码。
- **API 是 tagged union**：`render_cfg_t{ .type = RENDER_TEXT / RENDER_BITMAP / RENDER_FILL, … }`；
  文字支持 `word_wrap` 与逐行水平对齐（测量趟 + 渲染趟两阶段）。
- **渲染目标可插拔**：默认直写实屏；级联时 `app_screen` 注册自己的目标，把它写进画布（§7.3）。
- **显存持久化**：由 `app_render_persist_hook_fn_t` 接管（画布比实屏大，直存实屏会错位）。

## 12. 自检与诊断（`Application/…/BIST/`）

| 文件 | 定位 | 生命周期 |
|---|---|---|
| `app_test.c` | 硬件冒烟用例（像素扫描、字库渲染、灯序、板级 IO） | **休眠**——`app_boot.c` 里的调用被注释，发布版不跑 |

## 14. 板级抽象

`boards/<板>/` 是一块板的**全部差异**所在：

| 内容 | 说明 |
|---|---|
| `board.h` | 板级事实常量：屏与模组、级联网格 `BOARD_CASC_*`、画布开关、字库总量、IAP 记录开关、主卡格… |
| `board.mk` | 本板的源文件清单（供根 `Makefile` 合并） |
| `Core/` | CubeMX 生成的 `main.c`/`stm32f4xx_it.c`/`FreeRTOSConfig.h`（**不要手改**，重生成会覆盖） |
| `Application/ Device/ Platform/` | **覆盖**共享层的同名文件（板级驱动、板级通道、板级测试） |
| 链接脚本 | 板级 `FLASH_ORIGIN/LENGTH` + `INCLUDE Compiler/sections.ld` |

**级联/画布不是板名写死的**：由 `BOARD_CASC_COLS × BOARD_CASC_ROWS > 1` 推导出 `BOARD_CASC_ENABLED`，
并有一条 `#error` 兜底（"多卡必须开画布"）。所以"单卡板不编级联"是几何推导的结果，不是板名判断。
